# R1 CP/AP 官方基线构建

日期：2026-08-28。

## 为什么先做这一步

CPU0-only OpenVela 已经证明 R1 能启动 NuttX，但 Camera、Wi-Fi 和音频依赖的
原厂服务集中在 CP/AP 体系中。开始替换 AP 前，先原样编译官方工程，目的是确认
本地 SDK、工具链、分区生成和组合打包没有问题。这样后续失败时，可以判断问题
来自 OpenVela 接入，而不是官方工程本身。

本次只做了构建，没有把该镜像烧到 R1，也没有把官方 FreeRTOS AP 当作本项目
OpenVela 成果。

## 一次构建经过了什么

```text
projects/app_ab/partitions/bk7258/auto_partitions.csv
projects/app_ab/partitions/bk7258/ram_regions.csv
                         │
                         ├── 生成分区头文件、JSON 和链接地址
                         │
AP 配置、源码 ── CMake/Ninja ── bk7258_ap/app.elf 与 app.bin
CP 配置、源码 ── CMake/Ninja ── bk7258/app.elf 与 app.bin
                         │
bootloader + CP + AP ────┴── 打包工具 ── package/all-app.bin
                                              └── app_ab_crc.rbl
```

实际顺序是先构建 AP，再构建 CP，最后执行 `bk_build_package.py`。AP 和 CP 各有
独立 ELF，板上烧写的是打包后的组合镜像，不是单独烧写某一个 ELF。

## 分区关系

| 分区 | 起始地址 | 大小 | 作用 |
| --- | --- | --- | --- |
| `primary_bootloader` | `0x00000000` | 68 KiB | 上电后最先执行 |
| `primary_cp_app` | `0x00011000` | 1360 KiB | CP 固件 |
| `primary_ap_app` | `0x00165000` | 1156 KiB | AP 固件 |
| `s_app` | `0x00286000` | 2516 KiB | 升级/应用组合区 |
| `usr_config` | `0x004fc000` | 56 KiB | 用户配置 |
| `easyflash` | `0x007fa000` | 8 KiB | CP 持久化数据 |
| `easyflash_ap` | `0x007fc000` | 8 KiB | AP 持久化数据 |
| `sys_rf` | `0x007fe000` | 4 KiB | 射频校准数据，不能随意覆盖 |
| `sys_net` | `0x007ff000` | 4 KiB | 网络相关数据，不能随意覆盖 |

链接视角下，CP 代码从 `0x02010000` 执行，AP 代码从 `0x02150000` 执行；它们
分别对应 Flash 分区经过 BK 线性映射后的 CPU 地址。AP RAM 从 `0x28010000`
开始，CP RAM 从 `0x28064000` 开始，共享 `SWAP` 固定在 `0x2809f800`。这些值
由分区和 RAM 区域文件生成，后续 OpenVela AP 链接脚本必须与其一致。

## 构建结果

| 文件 | 字节数 | SHA256 |
| --- | ---: | --- |
| `package/all-app.bin` | 2646016 | 每次构建由脚本输出 |
| `package/app_ab_crc.rbl` | 2576384 | 每次构建由脚本输出 |
| CP `bk7258/app.elf` | 13159768 | `7a0ffb11552a7be8c49c3127b22f28e7b1e9c4869a4785eb16475bd20993a4b4` |
| AP `bk7258_ap/app.elf` | 6852716 | `09e7f2efb84aa8997ee8020cebb72fecea9d1fe27db5288b1450fdc4fb06aa31` |

两个 ELF 都是 32 位 ARM EABI5、静态链接并保留调试信息。构建摘要显示 CP Flash
使用 995492 字节，AP Flash 使用 467528 字节；这些只是官方空白 `app_ab` 的
基线，不代表换入 OpenVela 后的大小。

连续两次不改源码的增量构建中，CP/AP ELF 哈希保持一致，两个封装镜像的哈希
发生变化。对比发现差异集中在末尾 RBL 头：官方
`ota_packager_python.py` 会把输入文件的 `st_mtime` 写入头部，随后重算头部 CRC。
因此不能把封装镜像“每次哈希相同”作为当前官方打包链的退出条件。每次准备烧录
时仍必须记录当次哈希；判断代码是否变化时优先对照 CP/AP ELF、配置和分区文件。

## 得到的结论与下一步

已经证明：官方 SMP SDK、CP/AP 双构建、自动分区和组合打包在当前 Ubuntu 环境
可重复运行。尚未证明：OpenVela AP 能启动、Mailbox 控制台能交互，以及 R1 的
Camera/Wi-Fi/Audio 能从 OpenVela 使用。

下一步按以下边界推进：

1. 保持官方提交不变，以补丁或明确覆盖文件修改 CP；
2. 在队伍仓建立最小 `bk7258-ap` 芯片层和板级配置，只启 AP NSH；
3. 先让 UART0 经 CP 与 Mailbox 到达 AP 控制台；
4. 用 OpenVela AP 替换 `primary_ap_app`，仍由官方打包工具生成组合镜像；
5. 形成下一个实机验证节点，只验 CP 启动、AP NSH、`uname/sleep/free`。
