# R1 基础链路实机验证

日期：2026-08-28。本文是当前 R1 基础平台状态的事实来源，记录本队开发板上
已经实际运行的能力，不用公开候选实现或编译成功替代真机结论。

## 已验证结论

从源码修改到开发板运行的完整链路已经打通：

```text
Kconfig/defconfig
  → CMake/Ninja 选择并编译 NuttX、BK7258 芯片层、R1 板级层和应用
  → ld.script 链接生成 nuttx ELF
  → objcopy 生成 nuttx.bin
  → repack.py 组合 R1 bootloader、分区表和 CPU0 NuttX
  → all-app-openvela.bin
  → BKFIL 从 Flash 0x0 烧录
  → bootloader 启动 CPU0 NuttX
  → NSH 命令进行实机验证
```

实机已确认：

- BKFIL 能识别下载链路，完成擦除、写入、保护恢复和重启；
- CPU0 进入 `NuttShell (NSH)`，UART0 可以双向交互；
- `uname/free/ps/ls /proc` 正常，系统堆使用当前 336 KiB SRAM 窗口；
- Armv8-M SysTick 生效，`sleep` 可以按时返回；
- RAMLOG 注册为 `/dev/kmsg`，`dmesg` 可读到
  `BK7258 R1 bring-up complete`；
- KEY1、KEY2、KEY3 分别产生 `0x01`、`0x02`、`0x04`；
- KEY1 点亮红灯、KEY2 点亮绿灯、KEY3 同时点亮红绿灯。

## R1 基础 GPIO 映射

| 功能 | BK7258 引脚 | 电气行为 | 实测结果 |
| --- | ---: | --- | --- |
| KEY1 | P12 | 按下为低，内部上拉 | 通过 |
| KEY2 | P13 | 按下为低，内部上拉 | 通过 |
| KEY3 | P8 | 按下为低，内部上拉 | 通过 |
| 红灯 LED1 | P40 | 高电平点亮 | 通过 |
| 绿灯 LED2 | P41 | 高电平点亮 | 通过 |

初版把红/绿灯误写为 P41/P42，表现为 KEY1 和 KEY3 只能点亮同一颗绿灯，
KEY2 无灯。R1 原理图和 AIDK 示例均给出 P40/P41，修正后与实测一致。这个过程
也证明板级引脚应由 R1 原理图和真机决定，不能直接沿用相似开发板。

正式镜像使用固定名称维护：打包目录为 `all-app-openvela.bin`，复制给烧录工具
时为 `bk7258-r1-openvela-all-app.bin`。开发中更新同一文件；具体版本通过队伍仓
commit、打包生成的 `manifest.json` 和 SHA256 确认。需要长期保存的里程碑通过
Git tag/Release 或独立归档目录保存，不把功能说明不断追加到正式文件名。

`nuttx.bin` 的 SHA256 用于确认有效程序内容，完整镜像 SHA256 用于确认实际
烧录文件。实测发现 Beken packager 会改写分区末尾的少量填充字节，因此相同
`nuttx.bin` 重打包后完整镜像哈希不一定相同；manifest 同时记录两种哈希，验收
时必须记录真正烧录的那一个完整镜像。

## 尚未关闭的门禁

- P0：仍需完整记录 Flash、PSRAM、Camera、LCD、Audio 等实际器件型号；
- P1：构建和打包可重复，仍需完善校准区保护与恢复流程；
- P2：单次和多次交互已通过，仍需完成连续 10 次冷启动统计；
- P3：GPIO 已通过，PSRAM 边界和压力测试尚未完成；
- P4～P6：Wi-Fi/TLS、Camera、Audio 和非视觉反馈尚未完成。

因此当前结论是“R1 基础链路与 GPIO 通过”，不能外推为 BK7258 全部外设移植
完成，也不能把应用的图形、AI 或多媒体能力标记为已落地。
