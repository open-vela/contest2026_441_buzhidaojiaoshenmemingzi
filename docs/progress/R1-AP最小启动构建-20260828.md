# R1 AP 最小启动构建记录

日期：2026-08-28。

## 本轮目标

保留已经实机通过的 CPU0-only 镜像作为救援基线，另建隔离工作区验证下面的产品
启动链：

```text
CPU0 Armino CP → 启动 OpenVela AP → UART0/Mailbox → AP NSH
```

本轮先检查公开实现和构建契约，不把其他队伍代码直接复制到本队仓库。只有 AP
地址、ABI 和运行期内存全部正确，才允许进入组合打包和 R1 烧录。

- 官方 NuttX：`dd92bcf425738734d1b8aed09c2bd4dbe3f2e438`

  `d2ded037798530175e5dc5cde6fa1878f5d5ef35`

| --- | --- | --- |

## 第一次参考构建为什么不能烧录

135 参考的 AP 源码和预编译 SDK 归档能够在隔离工作区完成链接：

- ELF 入口：`0x02150000`
- `nuttx.bin`：164896 字节
- ELF SHA256：`c0960cf801b91200eeca5259b841d93a338f6a9dc93846d4adbbcef699d4fdad`
- BIN SHA256：`04814a1134ad4077a86976cb9daae6635175d81303591b8edc8163eb97d25f22`

但它的链接脚本把 RAM 定义为 `0x28050000..0x28097000`。已写入的段暂时仍在
`0x28050000`附近，看上去没有问题；运行期边界却是：

```text
_sheap  = 0x28054df0
_eheap  = 0x280967fc
_estack = 0x28096ffc
```

`_eheap` 和 `_estack` 已经越过 AP 上界 `0x28064000`，落入 CP RAM。因此这个
镜像即使编译成功，也不能和官方 CP 组合。它的入口函数还只运行 AP 生命周期
管理，没有启动交互 NSH。该产物未打包、未复制到发布目录、未上板。

这次排查说明镜像门禁必须同时检查：

1. ELF 入口、指令集和 hard-float ABI；
2. 原始向量表中的初始 SP 和 Thumb Reset；
3. AP Flash 大小及每个 LOAD 段；
4. `_eheap`、`_estack` 等运行期末端是否留在 AP RAM；
5. CP RAM 和 SWAP 是否完全没有 AP 占用。

对应检查已写成 `scripts/verify_r1_ap_image.py`。

## 264 参考复核结果

264 参考的板级头文件和链接脚本使用官方 AP RAM 边界，并实现了 CP/AP 控制台、
Mailbox 和外部 AP 打包链，方向与本项目一致。但当前提交的 `configs/nsh` 不能
原样完成链接：板级代码调用 `velasight_provisioning_load()`，配置却没有完整启用
配网模块及其依赖。隔离复核时依次补上了：

- `CONFIG_LVX_USE_DEMO_CONTEST2026_264_PROVISION_WEB=y`
- `CONFIG_NET_TCPBACKLOG=y`
- `CONFIG_PIPES=y`

前两项解决配网入口和 TCP backlog 依赖，第三项提供配网服务调用的 `pipe()`。
这些只用于还原公开参考的构建条件，不进入本队正式配置。参考仓文档还提到把 AP
物理分区扩到 4148 KiB，但公开提交没有包含对应的 `auto_partitions.csv`，因此这
一扩容步骤目前不能按仓库内容完整复现。

本轮继续使用官方 1156 KiB AP 物理分区。扣除 34/32 CRC 编码开销后，AP 原始
镜像上限为 `0x110000`，只有实际 ELF 和 `nuttx.bin` 都不越过该边界才会合包。
参考构建已经在隔离工作区完成，结果如下：

- ELF：1129312 字节；
- 原始 `nuttx.bin`：766784 字节（`0xbb340`）；
- ELF SHA256：`50bac6b28ed96f3f1bef367008765254ad2aff72a1a0d232ea5d714d1a4d699b`；
- BIN SHA256：`bc9440a2b9ff516b2f2bfce155507898abf4eb41200cee03444971546e0ebde6`；
- 初始 SP：`0x280395a0`；Reset：`0x02150141`；
- 运行期 heap：`0x280395a0..0x28064000`；
- Flash LOAD 有效载荷末端：`0x0220b340`。

`scripts/verify_r1_ap_image.py` 已放行该镜像。相同检查会拒绝 135 参考镜像，拒绝
原因是其 `_eheap`、`_estack` 和 CPU2 探测栈越过 `0x28064000`。这组正反例用于
确认门禁不是只看文件大小。

参考构建通过只证明公开链条可复现，不作为本队 R1 实机通过证据。

## 组合打包复核

在独立的 AVDK 工作树中应用 264 公开的 CP/AP 桥接改动，并用官方
`bekencorp/armino-idk:1.5` 环境构建 `projects/app_ab bk7258`。最终仍使用官方
分区：

| 分区 | 物理偏移 | 物理容量 |
| --- | --- | --- |
| `primary_cp_app` | `0x00011000` | 1360 KiB |
| `primary_ap_app` | `0x00165000` | 1156 KiB |
| `s_app` | `0x00286000` | 2516 KiB |

打包器内部将 CP 和 AP 原始镜像分别放在解码地址 `0x00010000` 与
`0x00150000`，AP 原始容量为 1088 KiB。打包临时文件 `app1.bin` 与上述
OpenVela `nuttx.bin` 逐字节相同，SHA256 同为
`bc9440a2b9ff516b2f2bfce155507898abf4eb41200cee03444971546e0ebde6`。

组合镜像 `all-app.bin` 为 2646016 字节，SHA256 为
`857410c4f491a37c53bebf63db134a4169e7fdc22d72599239c7aaf84a554bdf`。CP 的最终
配置确认启用了三核、AP 480 MHz、Wi-Fi VNET IPv4 和 GPIO 默认配置支持。

AVDK 的 `build_summary.txt` 仍会列出它顺带构建的原厂 AP 用量；这个数字不是
最终装入的 OpenVela AP 大小。最终内容以 `package/tmp/app1.bin` 的逐字节比较
为准。
