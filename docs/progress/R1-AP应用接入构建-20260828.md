# R1 AP 应用接入构建

日期：2026-08-28。

## 目的

在已经通过 R1 实机验证的 CP/AP 参考组合上，只增加本队 `vision_badge` 应用入口。
本节点不修改 CPU0、Mailbox、Camera、显示、Audio、Wi-Fi 和 CPU2，便于失败时把问题
缩小到应用接入或构建配置。

## 配置变化

AP 配置以已实测参考配置为基础，只增加：

```text
CONFIG_LVX_USE_DEMO_CONTEST2026_441_VISION_BADGE=y
```

构建系统生成并链接了
`apps/packages/demos/contest2026_441_vision_badge/libapps_vision_badge.a`。ELF 符号表中
存在 `vision_badge_main`、`camera_service_capture` 和 `vision_service_query`，可以排除
“配置已打开但应用未进入镜像”的情况。

  `490d4ce819575db5496e45719574584f086627e64ce2cae94495a7280fd85e9c`；

- `verify_r1_ap_image.py` 检查入口、向量表、ARM ABI、LOAD 段、Flash/RAM 边界、
  堆栈以及 ELF 与裸镜像一致性，结果为通过。

## CP/AP 合包结果

打包仍使用原分区：

- `primary_cp_app`：1360 KiB；
- `primary_ap_app`：1156 KiB；
- 最终 `all-app.bin`：2646016 字节；
- 最终镜像 SHA256：
  `81ce877c849e8e1ea6eb4313c3ba279645075e522d5c345b2dd165d1374e2b54`。

打包临时目录中的 `app1.bin` 与本次 `nuttx.bin` 大小和 SHA256 相同，且 `cmp`
逐字节一致。该结果证明最终组合镜像确实包含本次 AP，而不是打包缓存中的旧文件。

Windows 当前固定路径：

```text
G:\CIE\R1\firmware\cpap\bk7258-r1-openvela-all-app.bin
```

以后同一开发通道覆盖这个固定文件名；参考镜像、CPU0-only NSH 和救援镜像分别保留
在自己的目录，不通过给文件名不断增加功能后缀维护版本。

## 实机验证节点

烧录地址为 `0x0`。启动后在 CP 控制台输入：

```text
ap_console open
```

进入 AP 的 `nsh>` 后依次执行：

```text
help
vision_badge status
vision_badge selftest
```

预期 `help` 的 Builtin Apps 出现 `vision_badge`；`status/selftest` 应识别已经注册的
Camera 和 Audio 设备节点，并把尚未接入的云端能力保持为未就绪。当前不要执行
`vision_badge run`，因为 `camera_service_capture()` 仍是明确返回 `-ENOSYS` 的接口
占位。实机通过后再把已经验证的 V4L2 Camera/JPEG 路径接入该函数。
