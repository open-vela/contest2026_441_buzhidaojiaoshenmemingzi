# 验证与人工Review规范

## 提交前的实现者交付

| 项目 | 必须说明 |
| --- | --- |
| 需求 | 触发场景、预期行为与验收目标 |
| 设计 | 版本/API、分层、owner、锁、取消、deadline及恢复 |
| 差分 | 本次文件、关键修改、必要性与原有dirty差分的界限 |
| 验证 | 实际命令、源身份/配置、退出码、原失败及修复结果 |
| 交付 | 配置/依赖/镜像对应、剩余风险与回退 |

## 检查选择

- V01：先做diff检查与相应语言/格式检查，工具不可用明确记未执行。
- V02：对本次涉及接口选最小有效回归，覆盖正常、边界与错误；不为增加数量重复整套检查。
- V03：资源/并发变更覆盖取消、忙、队满、部分进度、迟到结果、重复进入及失败清理。
- V04：修复用例应能在缺陷仍在时失败；直接断言关键行为，不以搜索源文件字符串替代运行结果。
- V05：C单元/适配器尽量编入真实实现，mock限制在硬件或外部服务边界。
- V06：配置和平台变更通过唯一构建入口验证成对角色、依赖、ELF与布局，不只做语法检查。
- V07：构建/离线测试不推导实机效果；实际输出、显示、网络与功耗按对应方式证明。
- V08：性能标明起止点、单位、样本、版本与条件，阶段耗时不能冒充用户感知的端到端耗时。
- V09：保存失败样本和实际修复，不覆盖旧结果或将取消写成完整成功。
- V10：硬件或云操作在授权范围内执行，离线检查不得偷偷启动服务或产生模型调用。

## 维护者Review

需求适合使用者 → 层次与接口正确 → 资源/并发可闭合 → 错误可恢复 → 测试能约束缺陷 → 实现便于维护 → 版本与公开范围明确。

Review可以分为需求/设计/关键代码/验证四个范围，记录实际审查范围。自动检查与其他模型初审不填作人工审查，功能体验反馈也不自动等于逐行审阅。

AI按规则提交可供审阅的实现与证据，维护者选择接受或退回修改。未确认项保持未确认；禁止由实现者代填人工身份、批准时间和结论。

## 公开与版本

配置锁、源身份、dirty差分与镜像成套关联；提交说明描述问题、最终行为、验证与风险。正式内容按经过确认的文件选择，不直接推送带有私人历史的工作分支。

AI开发规范、Skill、案例和日志的公开范围由维护者确认。文件版本变化重新审查，格式校验通过不产生公开授权。真实记录不伪造，私人数据不全量带入。
