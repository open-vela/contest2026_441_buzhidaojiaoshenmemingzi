# BK7258 R1 移植计划

本计划优先建立最小平台基线，同时推进应用接口与主机测试。实机功能按其依赖
能力验收，不要求所有外设适配结束才开始应用开发。每个实机阶段都要求
“代码 + 构建日志 + 真机证据”，未留证据不得标记通过。

## 阶段与退出条件

| 阶段 | 工作内容 | 退出条件 |
| --- | --- | --- |
| P0 版本冻结 | 记录 R1 修订、SoC/Flash/PSRAM/Camera/LCD/Audio 型号；固定 openvela、PR 与 ARMINO commit | 硬件清单、原理图依据、commit 表完整 |
| P1 工具链与镜像 | 记录每条构建链的实际 Arm GCC；确认分区、链接地址、线性 CRC、备份/恢复流程 | 可重复构建和打包；当次镜像哈希留档 |
| P2 CPU0 最小启动 | 入口、向量、FPU、MSPLIM、堆、SysTick、UART0、IRQ；先只启 NSH | 冷启动 10 次进入交互 NSH；`free/ps/date` 正常 |
| P2B CP/AP 启动 | 保留 Armino CP，构建 OpenVela AP，打通 Mailbox 控制台和组合镜像 | CP 不重启；AP NSH 可交互；`uname/sleep/free` 稳定 |

## P0/P1 立即执行清单

收到硬件后先做只读确认和可恢复备份：

1. 拍摄板卡正反面、接口和丝印，记录 R1 标识；
2. 从官方/组委会获取 R1 原理图、BOM、Flash 分区与出厂固件；
3. 保存出厂固件、校准区、MAC/射频数据；没有恢复方案前不全片擦除；
4. 用原厂示例验证摄像头、双麦、扬声器、双屏、触摸、振动、NFC 与配网；
5. 记录 USB-UART 端口、115200 8N1 启动日志、Flash/PSRAM ID；
6. 再把 openvela 最小镜像装入已确认的应用分区。

当前官方 `bk_avdk_smp release/v3.1.1` 的 `projects/app_ab` 已原样构建通过，
确认了 CP/AP 分区、RAM 区域、Arm GCC 10.3.1 和组合打包链。该 SDK 构建与
CPU0-only OpenVela 使用的 GCC 13 工具链是两条链，记录时不能混写。下一步进入
P2B，先替换 AP，不同时接 Camera 和网络。

## 驱动优先级

应用最小闭环只依赖以下主路径：

```text
CPU0/NSH → PSRAM → Wi-Fi/TLS → DVP Camera/JPEG
                         └────→ 控制台反馈
```

因此按键、振动可以与网络并行，显示、NFC、陀螺仪、SD NAND 和低功耗放到
最小视觉闭环之后。双麦和扬声器属于第二阶段语音闭环，但应尽早做 60 秒稳定
采集，避免最后才发现 DMA/时钟冲突。

## Wi-Fi 适配方案

优先复用 `vendor_beken` 中同架构 Beken 芯片的 openvela Wi-Fi 桥接模式，分层为：

1. RF/PHY 与校准二进制保持厂商提供，不重写射频栈；
2. 在 chip/vendor 层封装初始化、STA、扫描、连接、断开和事件；
3. 映射为 NuttX `net_driver_s`/无线 ioctl，交给 openvela LwIP；
4. 验证 DHCP、DNS、TCP/TLS、掉线重连和校准数据保护。

若 BK7258 厂商库只支持 ARMINO/FreeRTOS，需要先确认许可和线程/同步依赖，
再做最薄兼容层；不能把完整 FreeRTOS 应用层一起带入 openvela。

## Camera 适配方案

1. 从 R1 原理图确认传感器型号、DVP 数据位宽、XCLK/PCLK/VSYNC/HSYNC 和 I2C 地址；
2. 先在原厂示例固定一个低分辨率 MJPEG/JPEG 工作模式；
3. 实现传感器 control、DVP/DMA lower-half 与缓存 ownership；
4. 对接 NuttX video/V4L2，使应用通过 `/dev/video0` 取单帧；
5. 帧缓冲放 PSRAM，DMA/cache 一致性明确，内部 SRAM 只保留控制块；
6. 测试超时、丢帧、坏 JPEG、反复 open/close 和 Camera + TLS 峰值。

## Audio 适配方案

1. 用相同声源分别录制两路原始 PCM，先验证通道、采样率和增益；
2. 接入 DMA 环形缓冲和 NuttX Audio lower-half；
3. 以 16 kHz/16 bit/单声道作为应用基线，AEC/NS 放在独立可开关层；
4. 麦克风与扬声器同时工作时测试回声、溢出、时钟漂移和 Wi-Fi 干扰；
5. 厂商算法库只按其授权方式链接，不把闭源库或密钥提交到队伍仓。

## 调试与证据

- 早期启动：UART 生命体征 + SWD，记录 PC/SP/VTOR/CFSR；
- 驱动：寄存器快照、逻辑分析仪时序、设备节点和错误码；
- 性能：每阶段堆、最大连续块、栈高水位、CPU 占用、吞吐和端到端耗时；
- 稳定：冷启动 10 次、模块循环 100 次、连续运行 2 小时；
- 回退：每次烧录前记录镜像哈希和恢复方法。

## 推荐提交顺序

上游改动保持单一职责：

1. `新增 BK7258 CPU0 启动与串口 NSH 支持`
2. `新增 BK7258 R1 板级配置与镜像打包`
3. `新增 BK7258 PSRAM 与基础外设支持`
4. `新增 BK7258 Wi-Fi 网络接口`
5. `新增 BK7258 DVP 摄像头与 V4L2 支持`
6. `新增 BK7258 音频采集与反馈支持`
7. `接入视障视觉辅助应用闭环`

每个提交先在本地通过审核，再 push。比赛期间新增的队伍 R1 板级适配放在专属仓
并通过 manifest 映射；若修改公共芯片层或已有公共代码，另按官方提交指南向
对应公共仓的比赛分支提交 PR。获奖后的上游贡献另行整理，不能把依赖的他人
公开移植当成本队新写的芯片支持。
