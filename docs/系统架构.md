# 系统架构

## 分层

```text
vision_badge 应用
├── workflow
├── camera_service
├── vision_service ───────────── MiMo Vision
├── audio_service
└── feedback_service
        │ 标准 openvela / NuttX 接口
        ▼
V4L2 / Audio / Netdev / GPIO / LCD
        │ BK7258 chip + R1 board 层
        ▼
DVP Camera · 双麦/AEC · Wi-Fi · PSRAM · Speaker · 振动 · 双屏
```

应用层只依赖标准设备接口和负 errno，不直接包含 ARMINO 头文件。Beken 厂商库
如必须使用，应封装在 `vendor_beken` 内，并明确线程、内存、许可证和多核边界。

## 核心数据链

```text
按键/语音触发
      │
      ▼
Camera Service ── V4L2 /dev/video0 ── 单帧 JPEG（PSRAM）
      │
      ▼
Vision Service ── wlan0 + HTTPS ── MiMo Vision
      │                                │
      └──── 有界结构化结果 ◀───────────┘
                         │
            ┌────────────┼────────────┐
            ▼            ▼            ▼
         控制台       Speaker/TTS    GPIO/PWM 振动
```

## 已验证的 CPU0-only 基线

```text
BootROM → Beken bootloader → CPU0 NuttX __start
                         → 向量/FPU/MSPLIM/时钟
                         → UART0 + IRQ + SysTick + heap
                         → board bring-up / PSRAM
                         → NSH / vision_badge
```

公开 bring-up 选择 CPU0 是为了直接拥有 UART0。最终是否保留厂商 CPU1/CPU2
固件及其 Wi-Fi/A/V 任务，要以 R1 SDK 的启动契约为准；任何跨核服务都要记录
mailbox/RPC、共享内存 ownership 和 cache 一致性。

该链路已经在本队 R1 上完成 NSH、SysTick、RAMLOG、按键和 LED 验证，继续作为
救援镜像和底层对照，不等于最终产品拓扑。

## 建议的产品启动链

```text
BootROM → Beken bootloader → CPU0 Armino CP
                            ├── 系统控制、无线控制器、UART0
                            └── 启动 CPU1/CPU2 OpenVela AP
                                      ├── Mailbox 控制台
                                      ├── NuttX 网络/媒体接口
                                      └── vision_badge
```

公开 264 队伍仓已经按此方向实现了 CP/AP 组合镜像及多项实板能力。这是当前最有
价值的工程参考，但尚未成为本队 R1 的实测结果。切换产品路线时先验收 AP NSH，
再按 Camera、网络、AI 的顺序接入，避免同时改变启动链和全部外设。

## 组合镜像怎样形成

官方 `bk_avdk_smp release/v3.1.1` 的 `projects/app_ab` 已在本机原样构建成功。
它不是把板级镜像和应用镜像分别烧录，而是先得到 CP、AP 两个独立程序，再依据
同一份 Flash 分区和 RAM 区域配置打成一个 `all-app.bin`：

```text
bootloader
   + CP app（当前保留 Armino）
   + AP app（后续替换为 OpenVela）
   + 分区/升级信息
              │
              └── all-app.bin ── 从 Flash 0 地址烧写
```

因此后续修改分为两类：OpenVela 的芯片层、板级层和应用层生成 AP 二进制；
`bk_avdk_smp` 负责 CP 固件、跨核契约和最终打包。两边必须共用同一组 AP Flash、
AP RAM、CP RAM、SWAP 和 PSRAM 边界，不能各自写一套地址。

组合前还要检查运行期边界。链接成功只能说明各段满足了当前链接脚本，不能说明
该脚本与 CP 使用同一份内存表。例如某个 AP ELF 的已初始化数据仍在 AP 区域，
但 `_eheap` 或 `_estack` 已经越过 AP 上界，启动后分配内存就会破坏 CP。项目用
`verify_r1_ap_image.py` 同时检查文件中的 LOAD 段和这些运行期边界符号。

首个参考组合包已经按这套规则生成：输入的 OpenVela AP `nuttx.bin` 与打包目录
中的 `app1.bin` 逐字节相同，官方 AP 物理分区仍为 1156 KiB。它当前只用于验证
CP/AP 启动和控制台链路；尚未经过本队 R1 实机测试，也不替代后续本队最小配置。

## 模块责任

| 模块 | 输入 | 输出 | 当前状态 |
| --- | --- | --- | --- |
| `workflow` | 用户问题、图像/结果缓冲 | 阶段和错误码 | 骨架完成 |
| `camera_service` | V4L2 路径、缓冲 | 单帧 JPEG | 节点探测完成；BK7258 驱动待 P5 |
| `vision_service` | JPEG、问题 | 有界文本/方向 | 接口完成；Wi-Fi/TLS/MiMo 待 P4/M5 |
| `audio_service` | PCM 缓冲 | 录音长度 | 节点探测完成；BK7258 音频待 P6 |
| `feedback_service` | 结构化结果 | 控制台/音频/振动 | 控制台基线完成，其余待 P6 |

当前未实现后端统一返回 `-ENOSYS`，避免调用方把占位实现当成功。

## 运行约束

- 每次只处理一个请求和一张图，不并发上传多帧；
- Camera、TLS、JSON 与 Audio 大缓冲错峰，真实峰值以真机测量为准；
- DMA 缓冲明确 cache clean/invalidate 和所有权切换；
- 请求/响应设置尺寸、连接和读取超时；
- API Key、Wi-Fi 密码、校准数据和私钥不进入仓库或 AI 日志；
- 云端不可用时返回明确错误并给出本地反馈，不生成伪答案。
